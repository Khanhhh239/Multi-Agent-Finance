**Verified for the M2 component gate on 2026-11-10.** The production validator
passed the planning and security contracts. The 15 development cases matched
the M2.1 baseline after passing through the gate.

## Acceptance evidence

| Criterion | Production evidence |
| --- | --- |
| Exact schema and trust boundary | Tests reject missing and extra fields, injected metadata, invalid status and malformed nested values. The M1 → M2.1 → M2.2 integration test seals a ready ranked plan. Nested date, filter and sort records are immutable and detached from the input. A clarification returns a separate type with a question and unresolved slots. |
| SQL injection and physical identifiers | Nine production security cases cover dimensions, filter field and values, identifiers, full-width SQL and an injected CTE in clarification text. Rejections use `invalid_request` and omit the payload. |
| Time and resource limits | Tests cover strict ISO dates, reversed and oversized ranges, flow and snapshot mode mismatch, the 750-day and top-k 100 boundaries, tighter server limits and rejection of a row cap above 1000. |
| Authorization and capabilities | Tests reject a forbidden view, forbidden metric, stale catalog, unselected metric and mixed periods. The gate reads current catalog capabilities and checks approval, verified handler, view, dimensions, filters and operation. |
| Server-owned metadata | The sealed plan receives tenant and policy hash from `AuthContext`, catalog hash from the current catalog and row cap from server policy. Missing operation uses the recorded `operation=aggregate` default. |

## Handoff

catalog hash and apply the sealed row cap together with top-k. The platform
demo uses its existing Text-to-SQL API and separate plan type. Partner filters
use the M2.1 code grammar and catalog compatibility. Existence of a partner
code in a particular warehouse snapshot is outside this gate.
