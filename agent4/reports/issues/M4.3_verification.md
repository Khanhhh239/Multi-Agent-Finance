## Case review

The first pass showed that the model could substitute a permitted metric for an explicitly restricted request. The second pass checked explicit registered metric labels and IDs against policy before selection. BM-114 and BM-138 stopped before model or SQL, and BM-111 correctly detected the explicit tax view. BM-115 through BM-118 returned unsupported before execution. Regression tests assert these early exits.

The second pass retained two security-tagged failures. BM-119 and BM-120 requested supplier-specific operating expenses. The model selected net profit margin, and plan validation stopped both. BM-100 requested an out-of-catalog CLV/CAC ratio and received a report on unrelated available metrics.

The third pass tested whether a shorter ranked candidate set would reduce unrelated selections. Dimensional breakdown/filter/top-k status improved from 4/20 to 15/20 and multi-metric status from 7/20 to 11/20. Single-metric aggregate regressed from 15/20 to 13/20, no-data/edge cases from 3/8 to 2/8 and clarification from 14/15 to 13/15. BM-100 returned unsupported before execution. The model selected `operating_expense` on BM-119 and BM-120, but the verified catalog lacks the requested supplier filter for that metric, so validation still stopped both. Planning-only clarification remains 15/15.

The executable catalog has independently checked M0.2 bindings, while v2 labels use canonical IDs such as `operating_expenses`. Some v2 invalid-metric flags reflect namespace coverage. Remaining failures span catalog coverage, selection, planning and contract differences in warning codes.

Release still needs domain-approved mappings and fixtures for canonical metrics, approved thresholds and a sealed test split. No independent result or answer judgments were available, and cost was unmeasured. All failures and coverage denominators are retained in the artifacts.
